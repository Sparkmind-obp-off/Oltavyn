# OLTAVYN — Full Agentic Affiliate OS Blueprint

Status: Architecture blueprint / implementation contract
Date: 2026-11-11
Target: OLTAVYN main, Affiliate OS product mode
Constraints: Cloudflare-first, Rp0-first, no paid execution without per-action approval, no GitHub Actions, no automatic publishing.

## 1. Product definition

OLTAVYN is the operating system and source of truth. Affiliate OS is its first focused product mode for an affiliate operator/creator. AVORLUNE remains the commercial brand and acquisition surface; it is not the engine.

This is not a chat wrapper around several APIs. It is a workspace coordinating a repeatable loop:

**Discover → Verify → Decide → Plan → Produce → Review → Publish → Measure → Learn**

The AI Agent is the primary command interface, while structured screens remain authoritative for inspecting and approving records. Every meaningful agent action must become a typed, auditable object in OLTAVYN—not disappear into chat text.

Initial market: Shopee Affiliate Indonesia, with distribution to TikTok, Shopee Video, Instagram, YouTube Shorts and Facebook. Platform eligibility is account-specific and must be checked by the operator.

## 2. Product principles

1. Evidence before claims. Every material product, commission, demand, policy or performance claim has a source, capture time, confidence, freshness and review state.
2. Agent proposes; policy authorizes. Read-only work may run within limits. Writes require typed tool permission. Paid data runs, link creation, approvals and publication require explicit confirmation.
3. No fabricated economics. Revenue, commission, conversion, sold count, ratings and search volume are unknown unless sourced. Estimates show assumptions.
4. Providers are replaceable. OLTAVYN owns canonical data, permissions, workflows, tool contracts, audit history and UX. Providers are not the source of truth.
5. One orchestration layer. The model selects tools from a registry; application policy validates every call. No arbitrary URLs, SQL, shell commands or provider requests generated by the model.
6. Human ownership. No credential, cookie, OTP or session-token collection. No unattended posting in the pilot.
7. Cost-aware by default. Manual/free path first; paid tools disabled until configured and separately approved. Enforce server-side limits and reconcile usage.
8. Recoverable operations. Long tasks are resumable, idempotent, observable and have explicit failed/needs-review states.

## 4. Provider strategy

| Capability | Default | Fallback / optional | Policy |
|---|---|---|---|
| Conversational/task LLM | Groq | Add a second compatible provider only after benchmark and budget review | Route by task; model allowlist; bounded tokens/timeouts; record provider/model/usage |
| Web search | Tavily | Manual URL/evidence capture | Search results are leads, not proof; capture URL, title, excerpt, timestamp and review state |
| Actor discovery | Apify Store | Scrape.ly Store | Discovery is separate from execution; inspect README, pricing, reliability, schema and output |
| Actor execution | One provider per approved task | Other provider only if capability/cost/reliability warrants it | Never dual-run by default; allowlist, schema validation, item/time/cost caps, explicit confirmation |
| Canonical application data | Cloudflare D1 | — | Source of truth |
| Private media/export | Cloudflare R2 | Manual/local during no-R2 pilot | Private by default; short-lived signed delivery |
| Live chat coordination | Existing Hono + D1 baseline | Durable Objects / Agents SDK when justified | Add for streaming, realtime, per-agent state or concurrency |
| Long-running tasks | Cloudflare Workflows | Queues for independent retryable jobs | Workflows for multi-step approval waits; Queues for fan-out/retry/DLQ |
| Cache/config | KV | In-memory cache | Never canonical evidence or financial records |

Specific decisions:
- Keep Groq as the initial inference adapter while account allowance and model quality meet needs. Groq supports local function/tool calling, where OLTAVYN—not the model host—validates and executes each tool call; this is the preferred pattern for fine-grained policy control. Do not assume unlimited free inference.
- Keep Tavily optional, not always-on. Its current pricing page advertises 1,000 monthly API credits on the free tier with no card; operations consume credits. The comprehensive Research endpoint was unavailable to this connected account during this audit, while Search remained callable. Add monthly app budgets and hard-stop when exhausted.
- Keep Apify and Scrape.ly as alternative adapters, not simultaneous defaults. Apify has broad Store discovery; its free plan includes platform usage, but after that allowance is consumed the platform may stop until the next cycle, and Store Actors can have separate pricing. Scrape.ly currently advertises $5 monthly free usage without a card, but compute, proxies, storage and paid Store Actor fees all draw from that credit; runs can be stopped when balance is insufficient. Evaluate each Actor independently; a platform free allowance does not make every Actor free.
- Do not enable Shopee scraping Actors for production harvesting by default. Shopee individual affiliate terms prohibit automated extraction methods for accessing/using Shopee intellectual property and confidential material. Use permitted official affiliate surfaces, user-provided URLs/data, approved exports or authorized APIs. Block Actors whose method or terms conflict with platform rules.
- Do not let a model decide affordability. Maintain verified Actor pricing/schema metadata, estimate costs, require confirmation and reconcile usage.

Provider routing evaluates capability fit, configured/validated state, policy eligibility, freshness, reliability, latency, estimated cost, budget remaining, privacy and fallback. If no provider passes hard constraints, use manual mode and explain why.

## 5. Agent architecture

### Control plane
- Intent classifier maps requests to allowlisted task classes.
- Planner creates a typed plan with outputs, tools, budget estimate and approval points.
- Policy engine checks user/workspace ownership, tool scopes, provider state, platform policy, cost budget and risk.
- Tool registry stores versioned JSON-schema contracts, read/write class, idempotency, timeout, rate limit and approval class.
- Orchestrator executes only validated calls; bounds steps, retries and context; records transitions.
- Verifier validates outputs, evidence requirements, source freshness and business rules.
- Response composer reports completed/not completed actions, citations, uncertainty, usage and next step.

### Capability domains
1. Workspace analyst: workspace state and next best action.
2. Market researcher: permitted public signals and evidence.
3. Product analyst: product fit, content potential, commission economics and risk.
4. Content strategist: audience/problem/angle/format briefs.
5. Creative producer: hooks, scripts, shot lists, captions, voiceover and asset prompts.
6. Compliance reviewer: claims, disclosure, intellectual property and platform rules.
7. Experiment analyst: hypotheses, outcomes and controlled tests.
8. Operations agent: tasks, approvals, status, retries and reporting.

Start with one orchestrator and specialist prompt/tool profiles, not eight autonomous agents. Split only when evaluation proves a benefit.

### Permission classes
- R0 Read: workspace, records, evidence, status. Allowed within workspace scope.
- R1 Research: web search or approved read-only retrieval. Quota-limited; external content is untrusted.
- W1 Draft/write: create brief, script, scorecard or content draft. Preview then confirm save.
- W2 Operational mutation: update product status, attach evidence, create experiment/task. Requires exact action summary and explicit confirmation.
- P1 Paid external execution: Apify/Scrape.ly or any metered API. Requires cost estimate, actor details, limits and explicit per-run approval.
- P2 Publish/external side effect: publishing, link creation or account action. Disabled in pilot; later per-action approval and platform-specific integration.

Model output can request a tool but cannot grant permission. Server validates every call immediately before execution.

## 7. Product UX and customer journey

### Navigation
- Home / Command Center: priorities, pipeline health, blockers, outcomes, next best action.
- AI Agent: persistent chat, task plan, tool activity, citations, approval cards and artifact previews.
- Discover: research briefs, market signals, product candidates and competitor references.
- Products: catalog, evidence completeness, scorecards and decision history.
- Content Studio: briefs, scripts, storyboards, assets, versions, compliance and export.
- Channels: registry, eligibility notes, publishing checklist and performance.
- Experiments: hypothesis, variants, schedule, observations and learning.
- Analytics: source-tagged performance and unit economics.
- Approvals: one inbox for save, paid execution, product selection and publishing decisions.
- Provider & Governance: provider health, model/actor registry, quotas, costs, policy versions and audit log.

### Main journey
1. First-run wizard: niche → audience → platform/channel → format → budget policy → operating target.
2. Agent creates workspace baseline and identifies missing data.
3. User requests product research; agent previews plan, sources, usage and any paid step.
4. Results appear as candidates with evidence state and explainable score breakdown.
5. User selects candidate; agent creates content brief and test hypothesis.
6. Content Studio presents versioned draft, claims linked to evidence and compliance checklist.
7. User approves export; user manually publishes and records URL/time.
8. Analytics imports permitted exports or user-entered metrics; agent recommends next experiment.

Interaction rules: show plan before multi-step work; allow edit/cancel; show provider, purpose, status, usage and source links; approval cards state exact action, estimated cost, limits, destination and reversibility; show partial/failure/stale states; every artifact has owner/workspace/version/source/timestamps/status; responsive and accessible UI.

## 8. Data architecture

Existing D1 entities remain canonical. Extend with normalized records rather than storing all task state in chat JSON.

Recommended migration-gated entities:
- agent_runs: intent, workspace, plan, state, current step, policy version, idempotency key and timestamps.
- agent_run_steps: ordered step, tool/version, input/output refs, state, retries, latency and error.
- tool_registry: schema/version, permission class, provider binding, enabled state and limits.
- provider_models: provider/model, capabilities, context/output limits, status and benchmark.
- provider_budgets: workspace/provider/period caps, reserved, consumed and hard-stop state.
- actor_registry: provider, actor ID, verified schema hash, pricing model/evidence, policy status and allowlist.
- approval_requests: exact action hash, permission, estimate, expiry, approver and decision.
- evidence_sources / evidence fields: source URL/publisher, captured/published time, field/value, method, confidence, freshness, review state and license/policy note.
- content_packages: brief/script/storyboard/caption/voiceover/assets, version and compliance state.
- publication_records: channel, post URL, time, content version, product/link reference and operator.
- performance_observations: metric/value/unit/period/source type/reference/entered_by.
- experiment_runs: hypothesis, variant, period, observations, result and next action.

D1 owns relational data and audit metadata. R2 owns large/private media. Durable Objects may own live coordination and per-run locks. Workflows own durable multi-step execution and approval waits. Queues own independent retryable tasks. KV is cache/config only.

## 9. Security and reliability

- Enforce auth, CSRF, workspace ownership and role/scope on every API and tool call.
- Validate schemas on ingress and provider output; cap payloads/context.
- Strict tool allowlists; block arbitrary URLs, SSRF, private IPs, arbitrary SQL, code execution and unbounded crawling.
- Treat web pages, actor output, reviews and uploads as untrusted prompt-injection data, never system instructions.
- Secrets only in Cloudflare bindings; redact tokens, auth headers, tracking URLs and personal data from logs.
- Rate limit by user/workspace/provider; enforce hard quotas server-side.
- Idempotency keys for writes; deduplicate retries.
- Approval payloads are immutable/hash-bound and expire; payload changes invalidate approval.
- Timeouts, retry/backoff, circuit breaker, dead-letter handling and cancellation.
- Audit every tool call, approval, mutation and external side effect.
- Add export/deletion and retention controls before public multi-tenant launch.
- Test prompt injection, cross-workspace leakage, replay, CSRF, SSRF, spend-limit bypass and duplicate execution.

## 10. Evaluation and production readiness

Quality evaluations: task success per workflow; evidence attribution; zero unsupported critical claims; tool selection/schema/policy accuracy; correct abstention; reproducible product scoring; compliance; regression isolation; cost per workflow; provider failure/latency/recovery.

Release gates:
- Gate A Foundation: migrations, typecheck, build, unit/smoke, auth/CSRF/workspace isolation.
- Gate B Read-only agent: validated Groq, safe R0/R1 tools, citations, quotas, prompt-injection tests and traces.
- Gate C Draft-writing: typed W1 tools, preview/confirm/save, idempotency and rollback.
- Gate D Durable workflows: resumable jobs, retries, cancellation, approval waits, notifications and DLQ.
- Gate E Paid research: actor registry, verified pricing/schema, hard budget reservation, per-run approval, usage reconciliation and kill switch.
- Gate F Pilot: one operator/workspace, Shopee-focused workflow, manual publishing, export and incident/rollback runbook.
- Gate G Public multi-tenant: privacy/terms, roles/quotas/billing, support, abuse prevention, SLOs, retention/deletion and load/security tests.

A gate passes only when exact tests and production evidence are recorded. A code commit is not a deployment.

## 11. Implementation sequence

### Phase 0 — Baseline audit
Confirm latest main SHA; inventory tables/routes/UI; run scripts and tests in safe local/preview; map tables to lifecycle; verify D1 migration state and Cloudflare bindings without production writes.

### Phase 1 — Agent runtime foundation
Wrap existing Groq chat with typed tool registry and policy engine. Add agent run/step ledger, tool traces and structured plan/result responses. Add model registry, task routing, provider health validation, context limits, cancellation and idempotency. Keep existing chat; do not create a second chat product.

### Phase 2 — Read-only intelligence
Build tools for workspace snapshot, products, evidence, channels, scorecards, content and experiments. Add optional Tavily search, source capture and evidence review. Add permitted Actor discovery/metadata lookup; no Actor run without explicit approval and policy eligibility. Add explainable product evaluation.

### Phase 3 — Controlled draft writes
Add tools to create product candidates, evidence drafts, scorecards, briefs, scripts, content packages and experiments. Each tool previews, obtains confirmation, revalidates and persists. Add versions and restore.

### Phase 4 — Durable workflows
Use Cloudflare Workflows for research-to-content pipelines and approval waits. Use Queues for independent retrieval, media processing and analytics import. Add Durable Objects/Agents SDK only where streaming, stateful coordination or concurrency justify it. Add progress events and resumable UI.

### Phase 5 — Paid execution and learning loop
Actor registry with schema/pricing verification, cost reservation and allowlists. Paid runs opt-in and per-run approved. Add permitted analytics imports and normalized observations. Close loop from results to experiment learning and next action.

### Phase 6 — Production pilot
Complete Gate A–F tests, migration/backup/rollback, Cloudflare secrets, private R2 delivery if needed, monitoring and operator runbook. Pilot one operator/workspace before public onboarding.

## 12. Current baseline and gaps (2026-11-11)

Present in main according to repository inspection:
- Hono/Cloudflare app, D1-backed workspaces and affiliate routes.
- Affiliate OS overview, products, detail, channels, AI Agent and Provider screens.
- Groq chat with workspace snapshot and persistent history (migration 0004).
- Optional Tavily research.
- Apify and Scrape.ly adapters with Actor allowlists and per-run confirmation/caps.
- Existing evidence, opportunities, content assets, experiments and scorecard context.

Not yet full agentic OS:
- Chat is request/response and read/analyze/draft; not a general typed tool-calling orchestrator.
- No durable agent run/step ledger, plan approval, policy engine or tool registry.
- Chat cannot safely create/update all business records through typed tools.
- No actor discovery-to-registry verification, output retrieval/import or budget reconciliation.
- Provider status checks secret presence, not live connectivity; audit counts are not monetary/token metering.
- No streaming, resumable progress or durable human approval waits.
- No end-to-end performance attribution/learning loop.
- UI is an MVP workbench, not yet unified command center/content studio/approval inbox.
- Migration 0004 and production deployment must be verified before calling chat production-ready.

## 13. Non-goals for initial build

No autonomous publishing, affiliate-link masking, account login automation, cookie/OTP collection or private platform scraping. No unbounded agent loops or autonomous spend. No forced use of every provider. No production-readiness claims based only on a successful commit. No replacement repository, GitHub Actions workflow or duplicate Affiliate OS.
